# 蓝策设计

## 背景与目标

当前「盘达」页面已有「主板策略」Tab。主板策略通过 T0 选股接口加载当日正式结果、竞价候选预览和历史归档，并在结果行中展示由形态统计计算出的「买入信号」灯色。

本次新增「蓝策」Tab，放在「主板策略」右侧。蓝策是基于主板策略结果的筛选视图，使用与主板策略完全相同的结果来源和展示结构，只在展示层过滤出 `买入信号 == blue` 的股票，帮助用户快速查看蓝色灯股票。

## 已确认的产品决策

| 项 | 决策 |
| --- | --- |
| Tab 名称 | `蓝策`；有结果时显示数量，如 `蓝策(3)` |
| 位置 | 紧邻「主板策略」右侧 |
| 过滤规则 | 严格保留 `买入信号 == blue` 的股票；其他灯色和无信号股票不显示 |
| 适用状态 | 当日正式结果、09:15～09:25 竞价候选预览、历史归档均使用相同过滤规则 |
| 股票展示 | 复用主板策略的股票卡片、点击打开同花顺、代码复制和蓝灯统计信息 |
| 排序 | 过滤后保持主板策略当前顺序，不新增蓝策专属排序规则 |
| 日期切换 | 按照主板策略现有日期选择、前一天/后一天导航和时间窗口逻辑 |
| 数据请求 | 与主板策略共用同一个 ViewModel、请求、轮询和缓存，不新增接口、不重复请求 |
| 无结果 | 显示蓝策专属空状态，不影响主板策略列表 |
| 加载触发 | 点击或滑动首次进入蓝策/主板策略时均可触发初始化加载；同一页面只初始化一次，日期切换仍按现有逻辑请求 |
| Tab 布局 | 5 个 Tab 支持横向滚动，保留现有标签顺序和可读性 |
| Web 构建 | 本次只修改源码和测试，不重建 `trading_app/build/web` |

## 总体方案

采用「共享数据状态 + 派生过滤列表」方案：

```text
/api/t0-selection
        |
        v
T0StrategyViewModel.results
        |
        +--> 主板策略：全部结果
        |
        +--> 蓝策：仅 buySignal == "blue"
```

后端返回的结果已经包含 `买入信号` 字段，蓝策无需修改 T0 选股逻辑、归档格式或 API 参数。过滤只发生在 Flutter 展示层，避免主板策略和蓝策出现两套请求、缓存或日期状态。

## Flutter 组件设计

### `T0StrategyViewModel`

在现有 `results` 之上增加只读派生列表，例如：

```dart
List<T0StrategyStock> get blueResults =>
    List.unmodifiable(_results.where((s) => s.buySignal == 'blue'));
```

该列表不复制或修改原始结果顺序。主板策略的排序、竞价实时行情合并和轮询逻辑保持不变；过滤后蓝策继续沿用蓝灯组内已有的标签优先、开盘涨幅等顺序。`results` 更新后，蓝策通过 getter 自动得到最新过滤结果。

这样可以保证：

- 竞价预览阶段，蓝策只显示候选中已经判定为蓝灯的股票；
- 实时行情更新时，蓝策沿用主板策略的排序和行情数据；
- 切换历史日期时，蓝策自动展示对应归档日的蓝灯股票；
- 主板策略与蓝策始终使用同一日期和加载状态。

### `RadarPage`

调整现有策略 Tab 区域：

1. `TabController`、`DefaultTabController` 和 `TabBarView` 从 4 个子项扩展为 5 个。
2. 在「主板策略」后插入「蓝策」。
3. 由于 Tab 数量增加，TabBar 改为支持横向滚动，保证小屏设备上标签仍可完整访问。
4. 主板策略和蓝策共用一次 `_lazyLoadIfNeeded` 触发逻辑；点击或滑动进入任一策略 Tab 时都能触发初始化加载，并由 `_strategyLoaded` 防止重复初始化。日期切换不受该标记影响，仍调用现有日期请求逻辑。
5. `_onTabChanged` 需要同时覆盖点击动画和 `TabBarView` 滑动后稳定的索引变化；只在策略 Tab 的索引真正切换到位时触发懒加载。
6. 抽取或参数化现有策略列表构建逻辑，使其接收 `blueOnly` 或明确的待展示列表：
   - `blueOnly == false`：使用 `vm.results`；
   - `blueOnly == true`：使用 `vm.blueResults`。
7. 日期栏、预热进度、错误状态、候选预览状态和历史状态继续使用同一套构建逻辑。
8. 顶部数量使用各自列表的长度：主板策略显示总结果数，蓝策显示蓝灯结果数。

蓝策处于预热或等待状态时，显示与主板策略一致的进度和提示；数据加载完成但没有蓝灯股票时，显示「暂无蓝色灯股票」。

## 数据流与状态行为

### 初次进入

```text
进入主板策略或蓝策 Tab
        |
        v
T0StrategyViewModel.loadAvailableDates()
T0StrategyViewModel.loadResults()
        |
        v
主板策略显示 results
蓝策显示 blueResults
```

若用户先进入其中一个策略 Tab，另一个 Tab 不再发起第二次相同请求；切换 Tab 只触发本地重建。

### 日期切换

两个策略 Tab 共享 `selectedDate`，并继续沿用主板策略现有的日期和时间窗口逻辑。在任一 Tab 选择日期或点击前后一天：

- 当天请求正式结果；
- 其他日期请求历史归档；
- ViewModel 更新 `results`；
- 两个 Tab 分别从同一份新结果派生自己的显示列表。

### 竞价预览

09:15～09:25 期间，主板策略显示候选列表和实时竞价涨幅，蓝策从同一批候选中只保留 `buySignal == blue` 的条目。蓝策不单独启动行情请求或轮询。

### 历史归档

历史归档仍通过现有 `archived=1&date=...` 请求读取。归档结果中的蓝灯字段沿用当前解析逻辑，蓝策只在客户端过滤，不改变磁盘归档内容。

## 错误处理与边界情况

| 场景 | 处理 |
| --- | --- |
| T0 请求失败 | 两个策略 Tab 共用现有错误状态；不显示过期的蓝策列表 |
| 正在预热 | 两个策略 Tab 显示相同预热进度和日期栏 |
| 竞价候选无蓝灯股票 | 蓝策显示空状态；主板策略仍显示完整候选列表 |
| 正式结果无蓝灯股票 | 蓝策显示「暂无蓝色灯股票」 |
| 历史日期无蓝灯股票 | 蓝策显示空状态，日期栏仍可继续切换 |
| 某条数据缺少 `买入信号` | 视为非蓝灯，不进入蓝策 |
| 切换 Tab | 不发起重复 API 请求，不重置共享日期选择 |

## 测试设计

### ViewModel 单元测试

在 `trading_app/test/t0_strategy_view_model_test.dart` 增加：

- 混合 blue、green、orange、空信号结果时，`blueResults` 只返回 blue；
- 蓝灯结果数量正确，原始 `results` 不被修改；
- 正式结果、候选预览和历史归档响应都能正确派生蓝灯列表；
- 日期切换后蓝灯列表随共享结果更新。

### 页面 Widget 测试

在 `trading_app/test/radar_page_test.dart` 增加：

- 页面包含 5 个 Tab；
- `蓝策` 位于 `主板策略` 右侧；
- `蓝策` 使用蓝灯数量而不是主板策略总数量；
- 蓝策列表显示蓝灯股票，不显示其他灯色股票；
- 蓝策列表顺序与主板策略过滤前的顺序一致；
- 蓝策页面仍包含日期切换控件和股票代码复制入口。

### 手工验收

1. 打开「盘达」，确认「蓝策」紧跟在「主板策略」右侧。
2. 在有多种灯色结果的交易日打开蓝策，确认列表只剩蓝灯股票。
3. 在 09:15～09:25 竞价预览时确认蓝策同样只显示蓝灯候选。
4. 切换前一天、后一天和下拉日期，确认蓝策显示对应日期的蓝灯结果。
5. 验证主板策略和蓝策之间切换不会重复请求或影响对方列表。
6. 验证没有蓝灯股票时显示空状态，主板策略仍正常显示。

## 非目标

- 不修改后端 T0 选股条件、买入信号计算规则或归档 JSON。
- 不新增蓝策专用 API、缓存目录或数据库表。
- 不改变主板策略的排序、卡片字段、竞价行情轮询和日期导航行为。
- 不修改当前工作区已有的数据库、缓存及 Flutter 构建产物改动。
- 本轮不自动重建 `trading_app/build/web`；如部署流程需要，待实现完成后按项目现有流程单独决定。
