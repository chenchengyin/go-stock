# 红策策略设计

## 1. 背景与目标

在现有雷达策略列表中，新增一个排在紫策之前的“红策”。红策不重新生成一份独立选股数据，而是复用主板策略同日期的选股结果 JSON，再使用同日期 Gob 中已加载的日线数据做二次过滤。

红策第一版需要支持：

- 页面加载方式、历史日期选择和主板策略一致。
- 使用主板策略同日期的 JSON 作为候选结果来源。
- 同一次请求只加载并解码一次 Gob，所有股票使用同一个内存日线 Map 完成过滤。
- 使用 Gob 中该股票实际最早一根日线的收盘价作为长期价格基准，不要求必须有完整 60 根日线。
- 保留 T-1 收盘价不低于该基准价的股票。
- 保留真赚率不低于 50%、达标率不低于 20% 的股票。
- 继续使用通用标红规则。
- 继续显示 `P`、`足`、`月` 标签，但红策标签从本次请求内存中的日线重新计算。
- 过滤条件采用可追加的过滤链，方便后续增加条件。

## 2. 不在本次范围内

- 不改变主板策略的筛选条件和排序规则。
- 不新增红策专用 JSON 归档文件。
- 不修改 Gob 的存储结构和抓取天数。
- 不把 Gob 日线数据发送到 Flutter 或长期保存到前端状态。
- 不改变通用标红规则的判定条件。

## 3. 模块与数据流

### 3.1 模块注册

新增模块编码：

```text
radar.red_strategy
```

显示名称为“红策”，排序位于紫策之前。后端模块注册和 Flutter 雷达模块定义都增加该模块，并沿用策略模块现有的访问控制方式。

### 3.2 请求流程

红策请求继续使用现有 `/api/t0-selection` 接口和 `module_code` 参数：

```text
Flutter 请求红策
    ↓
读取或生成主板策略同日期的 T0 结果
    ↓
读取同日期 Gob 一次
    ↓
构建日期到日线的内存 Map
    ↓
按红策过滤链逐只筛选
    ↓
对保留结果重新计算红策标签
    ↓
复用通用 DisplayRule 计算命中条件
    ↓
返回红策结果和数量
```

历史日期继续读取主板策略的 `t0_selection_<date>.json`，不因为红策请求重新抓取行情。当天请求沿用主板策略当前的生成、缓存和归档流程：如果本次刚生成主板结果，红策直接使用这次即将写入主板归档的同一批结果；如果已有归档，则使用该归档结果。红策只对主板结果做模块级二次筛选，不通过 HTTP 再调用主板接口，也不重复执行主板选股。

模块筛选必须发生在响应展示增强之前，保证返回的 `count` 与最终列表一致；展示增强只作用于已保留的结果。

## 4. 红策过滤规则

红策过滤链按以下顺序执行：

### 4.1 T-1 收盘价与实际最早日线比较

对主板 JSON 中的每只股票：

1. 从同日期 Gob 的 `Daily[ShortCode]` 取得该股票日线。
2. 按日期升序确定实际最早一根日线。
3. 取主板结果中的 `PrevClose`，即 T-1 收盘价。
4. 当 `PrevClose < 最早日线.Close` 时剔除。
5. 当两者相等时保留。

因此，股票不足 60 根日线时，使用实际最早数据，不因日线数量不足而单独剔除。Gob 中完全没有该股票日线，或无法取得有效 T-1 数据时，作为数据不完整进行保护性剔除，并记录过滤原因。

### 4.2 真赚率过滤

结果字段中的 `PatternFailPct` 为真亏率，红策计算：

```text
真赚率 = 100 - PatternFailPct
```

当真赚率小于 50 时剔除，即最终保留条件为：

```text
100 - PatternFailPct >= 50
```

### 4.3 达标率过滤

使用主板 JSON 中的 `PatternWinPct`。当达标率小于 20 时剔除，最终保留条件为：

```text
PatternWinPct >= 20
```

没有有效形态统计数据的结果不满足上述条件，第一版不进入红策列表。

### 4.4 可扩展过滤链

红策过滤器采用有名称的顺序规则集合，每条规则只负责判断当前股票是否保留。第一版加入价格基准、真赚率、达标率三条规则；后续增加条件时追加规则，不修改主板策略和通用展示逻辑。

过滤结果可以保留内部原因，便于日志定位，但不新增前端必需字段；接口仍返回现有 `T0SelectionResult` 结构。

## 5. 红策标签与标红

### 5.1 标签

红策返回前，使用同一次请求中已加载的日线 Map 和交易日截断逻辑，重新计算现有标签：

- 涨停破板：`P`
- 前一天跌停：`足`
- 前一天大阴线：`月`

标签计算不读取主板 JSON 中原有的 `Tag`，避免历史归档标签与当前 Gob 日线口径不一致。重新计算只修改红策响应副本，不修改主板 JSON 归档内容。

### 5.2 标红

红策沿用现有通用展示命中规则，并新增一条“两连涨停后竞价”规则：

- `任意K线＋涨停＋跌停`
- `涨停＋阴线标记`
- `涨停＋涨停＋阳线破板`
- `涨停＋非一字涨停后的开盘竞价`

其中现有“涨停＋涨停＋阳线破板”规则继续包含破板日收盘价高于开盘价的条件。新增规则要求 T-2、T-1 连续收盘涨停，且 T-1 不是一字涨停，随后 T0 竞价涨幅在 0.01%～3% 内。`DisplayRuleHits` 在模块过滤后计算，命中一个或多个规则时，Flutter 继续把股票名称显示为普通红色。

新增规则中，若 T-1 相对 T-2 收盘的开盘涨幅达到 3%，后端额外返回 `重点标红: true`，Flutter 才使用深红色；同一规则但 T-1 开盘涨幅低于 3%，以及其他标红条件组合，均保持普通红色。

## 6. 内存生命周期与性能

- 后端每个红策请求最多打开并解码一次对应日期 Gob。
- 所有股票共享该次请求的 `Daily` Map，不逐只重新读取文件。
- Gob 日线 Map 只存在于当前请求的局部处理范围内，不写入全局策略状态、不放入 HTTP 响应、不传给 Flutter。
- 过滤和标签计算完成后，不保留对 Gob payload 和日线 Map 的引用；函数返回后由 Go GC 回收。
- Flutter 切换日期时先清空红策旧结果和旧错误状态，只保留当前日期的结果状态，不保存 Gob 数据。
- 如果后续为了性能增加跨请求缓存，必须使用按日期的有界缓存和淘汰策略，不能无限保留历史 Gob。

## 7. 前端改动边界

Flutter 继续复用现有 T0 策略页面、加载状态、历史日期选择、结果卡片、百分比展示、标红展示和标签展示。需要增加：

- `redStrategy` 内容类型。
- 红策模块定义和排序位置。
- 红策模块状态初始化及结果数量读取。
- 红策模块对应的空列表提示和加载分支。

不在前端再次执行价格或百分比过滤，避免前后端口径分叉。

## 8. 错误处理

- 主板 JSON 不存在时，沿用现有主板策略的归档/预热错误行为。
- Gob 不存在时，不在红策请求中单独触发行情抓取；沿用当前日期缓存状态或返回数据未就绪状态。
- 单只股票日线缺失时只剔除该股票，不影响其他股票返回。
- Gob 解码失败时按现有缓存无效逻辑处理，不使用半成品数据。
- 过滤后为空列表时返回成功响应和 `count: 0`，由前端显示红策暂无结果。

## 9. 验证重点

- 模块排序为红策、紫策、主板策略、蓝策。
- 红策使用主板 JSON，且不产生独立红策归档。
- 60 根、少于 60 根和缺少日线三类数据分别符合设计口径。
- T-1 收盘价等于最早收盘价时保留，低于时剔除。
- 真赚率 50、达标率 20 的边界值保留，低于边界剔除。
- 标签来自内存日线，标红命中沿用三条通用规则。
- 历史日期切换后不显示上一个日期的红策结果，Gob 不进入 Flutter 状态。
- 同一个请求不会重复解码 Gob，也不会为每只股票重复读取文件。
